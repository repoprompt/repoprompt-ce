# M9.4 design: presentation detach, deferred handoff and bounded drain

Refs #1406 (parent roadmap #1401). Design and acceptance-test plan only. No production code or
tests change here.

- **Base:** `main` at `534e2c759` (M9.1 #1655, M9.2a #1659, M9.2b #1662 and M9.3a #1675 merged).
- **In flight elsewhere:** M9.2c (`runtime/20261110-m9-2c-writer-routing`: link steer/input,
  self-compaction, exact required-save writer, persistence forwarding), M9.2d
  (`runtime/20261110-m9-2d-admin-worktree`: administration and worktree commands), and M9.3b
  (window-free saved-target host cutover, phase B of the plan in `ledger.md` §"M9.3a phase A").
- **Line numbers** refer to the base commit. Paths under **AM/** mean
  `Sources/RepoPrompt/Features/AgentMode/`.

M9.4 must deliver five #1406 acceptance items:

1. Closing or changing a presentation cannot terminate an owned managed run, or silently elect
   another writer.
2. A UI visit during execution hydrates at the documented settlement boundary (deferred handoff).
3. Bounded retirement/drain completes before the writer is released.
4. The pending-start cancellation capability is stored before the session becomes visible; a
   visible starting session is already cancellable.
5. UI state stays MainActor-owned, and runtime isolation is explicit and justified.

## 1. Current behaviour and call paths

### 1.1 Ordinary window close cancels every run in the window

Each `AgentModeViewModel` (VM) owns a private runtime scope:
`private let runtimeSessionStore = AgentSessionRuntimeStore.shared.makeScope()`
(AM/ViewModels/AgentModeViewModel.swift:503). The process store holds scopes **weakly**
(AM/Runtime/AgentSessionRuntimeStore.swift:125-136), so live writer claims exist only while
something retains the scope. Today that is the VM, plus any in-flight task that captures the scope.

The close sequence:

1. `WindowContentView.onDisappear` (Sources/RepoPrompt/App/WindowContentView.swift:70-90) calls
   `windowState.beginClose()`, unregisters the window, then `Task { await windowState.tearDown() }`.
2. `WindowState.beginClose` (Sources/RepoPrompt/App/WindowState.swift:560-596) notifies
   `AgentSessionLinkRuntimeBridge.noteOversightWindowClosing` (bridge :2450, which parks
   reference-backed link pairs keyed by `endpoint.windowID`), closes Oracle background admission,
   fails unstarted commands, and calls `prepareForWindowClose()` on API settings, Context Builder,
   workspace and git VMs.
3. `WindowState.tearDown` (WindowState.swift:3117-3175) joins window saves and workspace
   activation, stops the domain presentation bridge and MCP routing registration, then
   `workspaceManager.cancelActiveSessions()` (:3157) and
   `agentModeViewModel.prepareForWindowClose()` (:3158). After that it stops the window's MCP
   server (:3162) and unloads workspace roots.
4. `AgentModeViewModel.prepareForWindowClose` (VM :5002-5027):
   - calls `runtimeSessionStore.beginRetirement()` **before the first await** (:5016). This
     refuses all new commands on the scope: `Writer.commandRejection` returns `.retiring`
     (AgentSessionRuntimeStore.swift:90-104), and `ControlActivationCancellation.permitsPublication`
     refuses (AM/Runtime/AgentSessionMCPRuntime.swift:310-313);
   - runs `performWindowClosePreparation` (VM :5029-5072): it unregisters observers, cancels UI
     refresh, and runs `prepareSessionForWindowClose` for every tab in parallel. It then stops the
     Codex and Claude coordinators and drains continuation starts, interaction effects and link
     Send/Stop effects;
   - only after that drain, calls `detachRunPresentation()` (:5026). The comment there notes the
     legacy path keeps terminal notifications until the drain finishes.
5. `prepareSessionForWindowClose` (VM :5117-5156) is the **close-cancels-run** body. It cancels
   ephemeral runtime state and pending question/approval/instruction, then tears down MCP control
   (`cleanupSessionStore: true`). If `runState.isActive` it calls
   `cancelAgentRun(tabID:origin: .internalLifecycle)` (:5143-5145, then
   `AgentModeRunService.cancelRun` at AM/Runtime/AgentModeRunService.swift:1476). It then disposes
   the provider, shuts down the Codex/Claude sessions, cleans MCP run routing
   (`reason: "window_close"`) and releases worktree ownership.
6. The scope is never explicitly released. `releaseWriterClaimsAfterDrain`
   (AgentSessionRuntimeStore.swift:376-390) is not called on this path. Claims disappear when the
   VM and any tasks capturing the scope deallocate. Production code has no explicit final-save
   acknowledgement gate here; tests join persistence with
   `test_drainSessionPersistenceAfterWindowClose` (VM :1253).

The user is told about this. `WindowCloseCoordinator.decide` (Sources/RepoPrompt/App/WindowCloseCoordinator.swift:114)
builds `activeWorkConfirmation` (:239): *"Closing this window will terminate … active agent
sessions"* / **"Close and End Sessions"**. The counts come from
`WindowState.makeCloseImpactSnapshot` (WindowState.swift:1285) via the workspace switch-session
registry, which reads `tabsWithActiveAgentRun`.

App termination (`WindowStatesManager.shutdownAllAgentSessions`, Sources/RepoPrompt/App/WindowStateManager.swift:1503-1548)
calls `prepareForWindowClose()` on every window VM, then
`shutdownPreparedOversightOwners(timeout: 2)`. Closing the last window terminates the app unless
MCP background mode is active (`AppDelegate.applicationShouldTerminateAfterLastWindowClosed`,
Sources/RepoPrompt/App/AppDelegate.swift:226-229).

### 1.2 Changing a presentation also terminates runs

- **Workspace switch inside a window.** After the switch confirmation, `WorkspaceManagerViewModel`
  runs `cancelActiveSessions()` (Sources/RepoPrompt/Features/Workspaces/ViewModels/WorkspaceManagerViewModel.swift:6573-6574).
  For Agent Mode this reaches `AgentModeWorkspaceSwitchSessionProvider.cancelSwitchSessions`
  (Sources/RepoPrompt/Features/Workspaces/WorkspaceSwitchSessionProviders.swift:104-123), which
  calls `cancelAgentRun(tabID:completion: .terminalPublished)` for every tab in
  `tabsWithActiveAgentRun`.
- **Tab switch** (`onTabChanged`, VM :5161) does not cancel; it only re-presents.
- **Rebinding the visible tab** to another session (`rebindPersistentSession`, VM :6287) refuses
  while the old binding owns a run (`bindingHasOwnership`, VM :6278-6284). This is non-terminating
  and elects no writer.
- **Stash/archive** cancels a live run by documented policy, and is authorised as `control`
  (docs/architecture/agent-session-oversight-auto-wake.md:285-294). It is an explicit lifecycle
  command, not a presentation change (decision D3).

### 1.3 Presentation attachment

- `AgentSessionPresentationRuntime` (AM/Runtime/AgentSessionPresentationRuntime.swift:13) is a
  per-scope `@MainActor` table of one `Sink` per exact session object. `attach` (:72) mints a
  generation token, and `detach` (:79) ignores stale tokens. Runtime owners call it whether or not
  a sink exists; activity is applied to the session even with no presenter (:145-157).
- The VM's `sessions` setter (VM :505-518) forwards to `runtimeSessionStore.replaceSessions` and
  then calls `synchronizeRunPresentationAttachments(previous:)` (VM :2134-2228). That detaches
  replaced objects and attaches a VM sink to new ones. Every callback is guarded by
  `sessions[session.tabID] === session` on the VM. Once `hasPreparedForWindowClose` is set, no new
  attachment is made (:2140).
- `detachRunPresentation` (VM :2230-2235) detaches all of them, and is called only at the end of
  `prepareForWindowClose`.
- **Gap:** `makeRunHooks` (presentation runtime :163-172) routes `notifyAgentTurnComplete` and
  `notifyAgentTurnFailed` **only** through the sink. A run with no presenter produces no
  turn-complete or turn-failed notification.

### 1.4 The one non-cancelling path today: prepared managed-oversight owners

Managed oversight targets that are not visible run in a nonvisual `WindowState` built by
`WindowState.makePreparedSessionOwner` (WindowState.swift:737-750). It has its own VM and scope,
and borrows the source window's API settings under a `retainForManagedRuntime` lease. The registry
lives in `WindowStatesManager+AgentSessionLinks.swift`:

| Step | Call path |
| --- | --- |
| Source window closes | `beginClose` → `detachPreparedRuntimeCarriers(from:)` (:113-129) moves the owner's location witness from the closing window to the private owner. The run continues. |
| UI visit enters | Three copies of the same code: `ensureSessionReady` (VM :7461-7490), `activateRoutedAgentSession` (VM :7518-7545), `rebindPersistentSession` (VM :6293-6307). Each calls `claimPreparedRuntimeVisit` (:89) and then `releasePreparedOversightOwnerForVisit` (:329-366). |
| Idle check | Release requires: no active `runState`, no active domain registration, `!preparedOversightRuntimeIsBusy()` (VM :2810-2823), and no preparation in flight. |
| Settle and hand off | `settlePreparedOversightHandoff` (VM :5720-5733) saves each session and requires `.saved/.notRequired` and `!isDirty`. Then `movePreparedOwnerToRetirement` (:435-444), `tearDownPreparedSessionOwner` (WindowState.swift:763-788), `finishPreparedOversightRuntime` (VM :5685-5711; this reuses `prepareForWindowClose`) and `releasePreparedOversightWriterAfterDrain` (VM :5713). After that the visible VM binds and hydrates from disk. |
| Busy: defer | `queuePreparedRuntimeVisit` (:100-103) stores the latest visit closure (latest wins). The visible VM returns an unhydrated session. |
| Resume at settlement | `schedulePreparedOversightCleanup` (:369-433) is woken by the owner's run observation (`agentSessionLinkInstallObservation`, :317-322). When the owner is idle it runs the queued visit (:425-426). On revocation or deletion it retires the owner and runs the visit only after an acknowledged drain (:446-457). |
| Failed durability | `finishRetiringPreparedOversightOwner` (:461-484) keeps the writer and the queued visit and posts the `prepared-runtime-unsettled` warning. Only an explicit visit or shutdown retries. |
| Quit | `shutdownPreparedOversightOwners(timeout: 2)` (:486-…) applies one absolute budget and reports a timeout as unsettled, never as durable. |

The oversight doc describes this contract:
docs/architecture/agent-session-oversight-auto-wake.md:51-64 ("*A visit during a run queues that
handoff and hydrates automatically when the run settles, without a second click or a duplicate
writer*").

### 1.5 Writer claims and retirement primitives (already in place)

- `AgentSessionRuntimeStore.resolveWriter` (:140-167) returns `.unavailable`, `.unique` or
  `.conflicting`. UI replicas never enter the store. A `Writer` carries
  `WriterIdentity{scopeID, incarnationID, workspaceID, restoration}`. `Command` admission is
  separate from originating ownership: `ownsPersistentClaim` (:108-114) keeps final IO legal during
  retirement.
- `Scope.beginRetirement` (:369) refuses new commands and new bindings for the session
  (`bindingRejection` → `.retiring`, :419-425; `hasRetiringWriter`, :180-185).
- `Scope.releaseWriterClaimsAfterDrain` (:376-390) is **scope-wide**. It needs: no in-flight saves,
  no pending attachment retention, no pending continuation starts, no link Send/Stop effects, and
  for every session: inactive, no composer attempt, no terminal commit in progress, and clean (or
  deleted).
- Per-session keying already exists for link effects (`drainPendingSendEffects(for:)`,
  AM/Runtime/SessionLinks/AgentSessionLinkExecutionRuntime+Send.swift:800), interaction effects
  (`drainPendingEffects(for:)`, AM/Runtime/AgentSessionInteractionRuntime.swift:210), attachment
  retention (`Retention.sessionID`, AM/Runtime/AgentSessionAttachmentRuntime.swift:157) and the save
  queue (`inFlightSessionIDs`). Continuation `pendingStarts` are keyed by a random UUID, not by
  session (AM/Runtime/AgentSessionRunContinuationRuntime.swift:13).
- `AgentRunTerminalCommitBarrier` (AM/Runtime/AgentRunTerminalCommitBarrier.swift:36) exposes
  `awaitTerminalPublication` (:514) and `awaitTerminalTeardown` (:528) for an exact
  `AgentRunOwnership`.

### 1.6 Pending-start cancellation today

- **MCP control activation is already correct.** `registerControlActivation`
  (AgentSessionMCPRuntime.swift:340-399) binds a `ControlActivationCancellation` (:289-331)
  atomically with the domain registration, before control is published. The capability retains the
  originating writer and scope, not a presenter. Direct/headless startup has the same property
  (ledger §"direct-host startup cancellation and drain").
- **The local composer start is not.** `AgentSessionComposerSubmitRuntime.claim`
  (AM/Runtime/AgentSessionComposerSubmitRuntime.swift:70-123) sets
  `session.activeComposerSubmitAttempt` (:115) and publishes `composerClaimChanged` (:121).
  `isComposerSubmissionInFlight` (AM/ViewModels/AgentTabSession.swift:372) then makes the session
  visible as starting to the composer, sidebar, monitor and link readiness, but no cancellation
  capability is stored. Managed Stop classifies that state as `.blocked(.targetBusy)`
  (AM/Runtime/SessionLinks/AgentSessionLinkStopTransaction.swift:46). Its `.pendingStart` admission
  (:56) covers only queued instructions and `mcpFollowUpRunPending`. `cancelRun` explicitly ignores
  pending starts (AgentModeRunService.swift:1484-1488); `withdrawPendingStartForSessionLink`
  (:1465-1474) handles only the queued-instruction scope.
- Runners set the attempt and `.running` synchronously before the first provider await
  (AgentModeRunService.swift:458-462). Once running, active-run cancellation applies.

### 1.7 Gap summary

| Acceptance item | Current state |
| --- | --- |
| Close/change cannot terminate | Close cancels (§1.1); workspace switch cancels (§1.2). Only prepared oversight owners survive. |
| No silent writer election | Holds by store construction, but close drops the claim by scope disposal rather than an acknowledged release. |
| Visit hydrates at settlement | Implemented only for prepared owners, in three duplicated VM entry points. |
| Bounded drain before release | Prepared owners: yes. Ordinary close: no explicit release or acknowledged final save. Release is scope-wide only. |
| Pending-start capability before visibility | MCP control and direct startup: yes. Composer start, typed ACP follow-up and worktree preparation inside a start: no. |
| MainActor UI, explicit isolation | UI is MainActor. Runtime owners are `@MainActor` by inheritance from `AgentTabSession`, which is not documented as a decision. |

## 2. Target design

### 2.1 Vocabulary and invariants

- **Host.** The runtime owner that retains one `AgentSessionRuntimeStore.Scope`. It installs that
  scope's execution (`AgentModeRunService`), link execution, interactions, MCP route, provider
  coordinators, storage inputs and the API-settings lease. M9.3b introduces this type for saved
  targets. M9.4 makes it the only way any scope is retained.
- **Presentation lease.** A VM's attachment to a host. It consists of the sink attachments, the
  VM's UI state, and the tab/window/workspace that displays the host's sessions. It holds no writer
  claim and no runtime capability.
- **Detach.** Dropping a presentation lease. It never calls `beginRetirement`, never cancels a run,
  never disposes a provider and never changes a `WriterIdentity`.
- **Retire.** The host fences new admission for a session (or for the whole scope), joins that
  session's drain set, acknowledges the final save, then releases that session's claim.
- **Settlement boundary.** The quiescence predicate in §2.4.

Invariants:

- **I1 – Identity continuity.** A session's `WriterIdentity` (scopeID and incarnationID) is the same
  before and after any presentation change. Only retirement and release end it.
- **I2 – No gap.** No window close, workspace switch or visit has an interval in which
  `resolveWriter` for a live-owned session returns `.unavailable(.absent)` or `.conflicting`.
- **I3 – Presentation is optional.** Every runtime effect, including terminal publication,
  persistence, notifications, link delivery and interaction settlement, completes with zero
  presenters. Sinks only project.
- **I4 – Atomic handoff.** Releasing a host claim and installing the visiting scope's
  restoration-pending claim happen in one synchronous MainActor section, with no suspension between
  them.
- **I5 – Release after acknowledgement.** A claim is released only after its drain set is joined
  and its final save is acknowledged by the exact originating writer. A timeout never releases a
  claim; it reports the session as unsettled.
- **I6 – Cancellable before visible.** Any state that makes a session look like it is starting or
  running (composer claim, run state, MCP `running`, sidebar/monitor "starting") is published only
  after an exact cancellation capability for that start is stored in the runtime.
- **I7 – Disjoint owners preserved.** The authorization engine and the four link owners (link,
  notices, claim, wake), plus `AgentRunAttemptLifecycle`, `DomainAgentRunSessionStore` and
  `AgentRunTerminalCommitBarrier`, keep their roles (#763). M9.4 adds no lifecycle manager, store
  or registry. The host registry is the one M9.3b introduces to replace `preparedOversightWindows`.

### 2.2 Ownership after detach

**Every scope has a host from creation.** The visible VM no longer calls `makeScope()`. It acquires
a presentation lease on a host built by the host composition, and its `sessions` accessor forwards
to `host.scope.sessions`, as it forwards to the private scope today.

That makes close and detach trivial for identity. The scope, run service, MCP route, link
endpoints and provider controllers were never window-owned, so nothing has to move. Moving a live
session between scopes is **not** an option: it would change `scopeID` and invalidate every
originating receipt (control contexts, question waits, Codex response receipts, terminal
revisions) that M9.2 built.

**Precondition P1 (load-bearing).** At the moment a run starts, every identity it uses (route ID,
link endpoint, MCP route binding, workspace/context inputs, API-settings lease, run service and
coordinators) must belong to the host, not the window. If visible-window runs still start with
`routeID: windowID` (VM :3305 and :3344), the window's MCP server, or the window's
`WorkspaceFileContextStore`, then a detached run would lose its tool route and context mid-run.
Rebinding a live run's route is out of scope and unsafe. M9.4 therefore depends on visible
execution being host-composed. Under decision D7, M9.3b delivers that cutover (§2.11 a, §3.2).

**Host retention predicate.** A host is retained by the host registry while any of these holds:

- a presentation lease is held;
- a session has live work: `runState.isActive`, `terminalCommitInProgress`, an active composer
  claim, a pending start, a pending interaction (question, approval, worktree review, hook review)
  or a pending queued instruction;
- an effect is in its drain set (§2.5);
- a session holds a committed live-consent link as observer or target. This keeps the current
  prepared-owner rule (`schedulePreparedOversightCleanup` :386-391) and the oversight doc's "closing
  the source window does not … discard a live-consent link".

**Per-session classification at detach.** A window host holds every tab's session. When the last
lease drops, the host classifies each session:

- **Retained:** live work or a live-consent link (warm). The session stays in the scope with no
  presenter.
- **Retiring:** everything else. The host retires the session individually (§2.5), so that another
  window can bind it immediately.

The host itself is disposed when its scope has no sessions. This needs a **per-session release**
primitive alongside the scope-wide one (§2.5).

### 2.3 Detach protocol

**Window close** (replaces §1.1 steps 2–6 for Agent Mode):

1. *Presentation teardown (VM, synchronous).* Unregister observers, cancel UI refresh tasks, drop
   transcript presentation records and the pending UI refresh map (today's VM :5030-5056 UI
   subset). Then detach every sink attachment through the host lease.
2. *Notification fallback.* Once a session has no presenter, the host's detached sink (§2.8)
   receives terminal and attention notifications.
3. *Lease release.* `host.releasePresentationLease(lease)` is synchronous. Classification and
   per-session retirement run as host-owned tasks; the window does not join them. Window teardown
   must not wait for a background run.
4. *Link bookkeeping.* Endpoints are host-route keyed (P1), so `noteOversightWindowClosing` and
   `invalidateWindow(reason: .windowClosed)` do not apply to host-owned endpoints. They fire only
   when a **host** retires a session: "endpoint retiring" replaces "window closing" as the parking
   trigger for `AgentSessionOversightLaunchCoordinator.noteWindowClose` (bridge :2450-2462).
5. *Window-only teardown continues unchanged:* context builder, workspace saves, prompt and git
   VMs, the window MCP server's presentation role, and workspace root unloading.

**Close confirmation (D1).** Every writer-owned run detaches on close, whether it is a user run, a
link-managed run, an MCP-controlled run or a delegation child. `activeWorkConfirmation` changes
from *terminate* to *keep running in the background*. Its default action closes and keeps sessions
running. A secondary action, **"Stop Sessions and Close"**, issues ordinary explicit Stop commands
through the writer (with Stop receipts, `origin: .explicitStop`) before detaching. That is the
only way closing a window ends a run, and it is an explicit Stop. Close itself never cancels.

**Last window closed with live hosts (D4: automatic background mode).**

1. `AppDelegate.applicationShouldTerminateAfterLastWindowClosed` (AppDelegate.swift:226-229)
   returns `false` while **either** MCP background mode is active (unchanged) **or** the host
   registry reports background-blocking work. The decision is a pure static policy function so it
   can be unit-tested.
2. **Background-blocking work** is any host session with live work: active run, terminal commit,
   pending start, pending interaction, queued instruction, or a drain in progress. It also includes
   any host in the `unsettled` state (failed final save or wedged drain), so that losing a failed
   save never happens silently. A session retained *only* as a warm live-consent link endpoint
   does not block termination. On quit its intent parks and restores at the next launch, as today.
3. While windowless, the app keeps its Dock presence. Runs continue, the detached sink (§2.9)
   posts turn-complete and needs-attention notifications, and reopen
   (`applicationShouldHandleReopen`) or a notification action opens a window whose visits use the
   §2.6 handoff.
4. When the last background-blocking host settles and retires, and there is still no window and MCP
   background mode is off, the host registry asks the app to terminate through the ordinary
   termination path. By that point everything is settled, so the shutdown drain is trivial. If a
   window was opened in the meantime, nothing terminates.
5. **Explicit quit** (⌘Q, menu or Dock) is never blocked by background work. It keeps the bounded
   2 s drain over all hosts (§2.5) and reports unsettled work as unsettled, never as durable. Quit
   cancels live runs. That is a quit decision, not a close, so D1 still holds.
6. The last-window close confirmation says the app will keep running in the background until the
   sessions finish, and that quitting stops them.

**Workspace switch inside a window (D6: one host per window × workspace epoch).**

- `AgentModeWorkspaceSwitchSessionProvider.cancelSwitchSessions` stops cancelling, and the
  "active agent sessions" item becomes informational in the switch confirmation.
- A switch drops the window's lease on the old epoch's host. That host classifies its sessions as
  at close (§2.2): live sessions keep running there, and idle ones retire per session. The window
  then attaches to a host for the new workspace.
- When the window activates workspace W, it re-leases its own previous host for W if that host is
  still alive, with no handoff or hydration, because these are the same objects. Otherwise it
  creates a new epoch host. A window never holds two hosts for the same workspace at once.
- Idle tabs restored into a re-leased host hydrate normally. Sessions that are live in *another*
  window's host go through the §2.6 deferred visit.

**Tab switch** is unchanged; add a regression test. **Rebind** stays refusing; the queued visit
goes through §2.6.

### 2.4 Settlement boundary

`Scope.settlement(for session) -> Settlement` is one synchronous MainActor query. It consolidates
`preparedOversightRuntimeIsBusy` (VM :2810), the idle checks in
`releasePreparedOversightOwnerForVisit` (:341-345) and the per-session half of
`releaseWriterClaimsAfterDrain` (:378-387). A session is **settled** when all of these hold:

1. **Run quiescence:** `!runState.isActive`, `!terminalCommitInProgress`, no `activeRunOwnership`.
   If `lastTerminalCommitRevision` exists, the barrier has completed its publication **and**
   teardown for that ownership.
2. **No pending start:** no composer claim, no continuation producer for the session (needs
   session-keyed `pendingStarts`), `!mcpFollowUpRunPending`, no queued instruction eligible for
   automatic delivery, and no self-compaction admission in progress.
3. **Provider quiescence:** no pending Claude provider adoption or work, and no Claude turn in
   flight on the exact controller (the async probe from VM :2814-2820, re-validated after the await
   against the start/stop fence), and no Codex turn pending.
4. **No domain registration:** `AgentRunSessionStore.hasActiveRegistration(sessionID)` is false, or
   the registration is idle control that the handoff will deactivate. Treat this as an async
   precheck that is re-validated.
5. **No session effects:** no link Send/Stop, interaction or attachment-retention effect, and no
   in-flight save for this session.
6. **Durable:** the exact-writer required save (M9.2c checkpoint 11) returned `.saved` or
   `.notRequired` with `!isDirty`, or the session is permanently deleted.

Items 3 and 4 are async probes. The protocol in §2.6 re-checks the synchronous items in the same
MainActor turn as the release (I4), so a run that starts during a probe await invalidates the
handoff.

A `waitingForUser/Question/Approval` run is **not** settled. §2.6 handles those through runtime
commands, so a deferred visit cannot deadlock on its own approval (R2).

### 2.5 Bounded retirement, drain and writer release

**Drain set Δ(s).** At retirement start the host sets a per-session retirement fence. New command
admission for *s* is refused (`.retiring`), while `ownsPersistentClaim` keeps originating final IO
legal. The host then captures a finite join set. Nothing admitted after the fence can join it:

| Effect | Existing owner / join |
| --- | --- |
| Continuation starts for *s* | `AgentSessionRunContinuationRuntime` (key by session; today `drainPendingStarts` is scope-wide) |
| Link Send/Stop effects | `drainPendingSendEffects(for:)`; the Stop drain likewise |
| Interaction effects | `AgentSessionInteractionRuntime.drainPendingEffects(for:)` |
| Terminal publication + teardown | `AgentRunTerminalCommitBarrier.awaitTerminalPublication/Teardown` for the last ownership |
| Oracle background | `awaitOracleBackgroundDrain(for:)` (existing 30 s bound) |
| MCP control | `teardownMCPControl` deactivation and registration cleanup |
| Provider | `disposeProviderIfPresent`, then Codex/Claude session shutdown. **Only at retirement, never at detach.** |
| MCP run routing | `cleanupMCPRunRoutingIfPresent(reason: "host_retired")` |
| Worktree ownership | `releaseSessionWorktreeOwnership` (M9.2d routes this through the writer) |
| Attachment retention | `AgentSessionAttachmentRuntime` (per `sessionID`) |
| Final save | Exact-writer required flush, acknowledged |

**Release.** `Scope.releaseWriterClaim(for session) -> Bool` is the per-session analogue of
`releaseWriterClaimsAfterDrain`. It removes the session from the scope map, which drops its live
claim through `updateLiveSessionBindingIndex`, only if the settlement predicate still holds, the
session's retirement fence is set, and Δ(s) has joined. The scope-wide method stays as the
"every session" special case used at shutdown.

**"Bounded" means two things:**

1. **The join set is finite and fenced.** It is captured under the retirement fence and joins only
   effects that already exist. Each effect uses its owner's existing bound: Stop teardown deadline
   and `retireTimedOutManagedStopIfEligible`, the 30 s Oracle drain, the domain shutdown deadline.
2. **Deadlines never cause release.**
   - *Non-quit retirement* (idle at close, settled visit, revoke, delete) has no forced release
     deadline. Under D5, a soft deadline escalates the warning only. If Δ(s) or the final save
     fails, or the soft deadline passes, the session stays retained and enters a visible
     `unsettled` state with the existing `prepared-runtime-unsettled` warning. An unsettled host
     blocks automatic background termination (D4). It is retried on an explicit
     visit, on durable deletion (a tombstone is a new settlement fact, as today at :378-384), or at
     shutdown.
   - *Quit* reuses one absolute budget: the existing 2 s from `shutdownPreparedOversightOwners`,
     now applied to all hosts. Timeout returns `false` and is reported as unsettled. Process exit
     is not a release receipt.

**Revocation and deletion during a detached run** keep today's policy: cancel and retire
(`retirePreparedOversightOwner(preservingIntent: false)`). That is an authority decision, not a
presentation change, so acceptance item 1 is not violated.

### 2.6 Handoff protocol for a UI visit

There is one entry, `AgentSessionPresentationHandoff.visit(sessionID, into: lease, intent:)`. It
replaces the three duplicated blocks at VM :6293-6307, :7461-7490 and :7518-7545. It reuses the
claim, queue and resume semantics of `claimPreparedRuntimeVisit`, `queuePreparedRuntimeVisit` and
`schedulePreparedOversightCleanup`.

```text
visit(s) ─▶ resolveWriter(s)
   .unavailable(.absent) ─▶ ordinary cold hydration (M9.3a loadRuntime / VM load)
   .conflicting          ─▶ fail closed; visible "session open elsewhere" error, no election
   .unique(w), w.scope is the visiting lease's own host ─▶ re-present (same objects); done
   .unique(w), other host H:
       claimVisit(s)            (latest-wins; an older queued visit is superseded)
       if H.settlement(s) == .settled after async probes:
           H.beginRetirement(s); join Δ(s); exact-writer final save
           ── one MainActor section, no await ──
           re-check settlement sync items and w.isCurrent
           H.releaseWriterClaim(s)
           visitingScope installs restoration-pending claim (M9.3a pattern)
           ─────────────────────────────────────
           visiting VM hydrates from disk; presentation attaches
       else:
           queue visit; show placeholder (below); resume when H's run observation
           (monitorReadinessChangePublisher / runState) reaches settlement
```

**Placeholder during a deferred visit.** The visiting tab shows a read-only projection from
`w.query()` and the scope's monitor projections: run state, elapsed time and latest activity.
Commands route through the existing process-writer routing (M9.2a "Send/Stop … through the
process writer"):

- **Stop** routes to *H*'s writer and returns a Stop receipt.
- **Pending interactions** (question, approval, worktree review, hook review) render from the
  interaction runtime and are answered through its captured commands (M9.2b checkpoints 2–9). They
  do not need hydration. This breaks the "visit waits for settlement, settlement waits for approval"
  deadlock.
- **Composer input** is kept as a local draft. Submit is refused with "opens when the current run
  settles" (D2). It does not steer *H* in M9.4.

**Hydration point.** The visit hydrates exactly once, after the boundary, from the acknowledged
payload. Run output is therefore in the transcript without a second click, and no duplicate writer
ever exists (I2, I4).

**Supersession and cancellation.** A newer visit for the same session replaces the queued closure;
a visit for a different session cancels nothing. Closing the visiting window, switching its
workspace or rebinding its tab invalidates the queued closure; the existing resume guards check
`activeWorkspaceID` and `activeAgentSessionID(forTabID:)`. Deletion drops the queued visit. A
failed final save keeps the visit queued, and an explicit re-visit retries the save (today's
`releasePreparedOversightOwnerForVisit` :330-336 behaviour).

**Race with new work.** If a wake, MCP send or follow-up admits a new run on *H* while the visit's
probes are suspended, the synchronous re-check fails and the visit re-queues. If the visit wins the
synchronous section, later commands resolve to the visiting scope's writer, which is
restoration-pending and then hydrated. Commands admitted before hydration are refused with
`restorationUnavailable`; they are not routed to *H*.

### 2.7 Failure and timeout semantics

| Situation | Outcome | Writer | Receipt / user signal |
| --- | --- | --- | --- |
| Close during active run | Detach only; run continues | Unchanged (I1) | Confirmation copy; sidebar/monitor "running in background" |
| Close with idle sessions | Per-session retirement | Released after ack | None on success |
| Final save fails at idle retirement | Session retained, `unsettled` | Retained (`.retiring` refuses successors) | `prepared-runtime-unsettled` warning; retry on visit or shutdown |
| Δ(s) effect never completes (provider hang) | Retained, `unsettled` | Retained | Warning; Stop remains available; quit budget applies |
| Visit during run | Queued, placeholder | Unchanged | Placeholder; hydrates at settlement |
| Visit and save failure at settlement | Visit stays queued | Retained | Warning; explicit re-visit retries |
| Revocation or deletion during detached run | Cancel and retire (existing) | Released after drain, or deletion tombstone | Existing scope-ending evidence |
| Last window closed with live hosts (D4) | App stays running without windows; runs continue | Unchanged | Close-confirmation copy; detached-sink notifications; terminates automatically once settled |
| Last window closed, only warm-link hosts | App terminates through the normal path | Parked by the existing quit policy | Existing launch restoration |

### 2.8 Pending-start capability before visibility (I6)

1. **Composer start.** Add an exact `AgentRunPendingStartCancellation` (or extend
   `AgentRunCancellationAdmission` scope `.pendingStart` with a composer variant) to the scope's
   startup or submissions runtime, keyed by session identity. It captures the writer command (or the
   creation handle, for an unbound first send), the attempt ID, the `AgentRunStartStopFence` and
   the draft-restoration payload. Inside `AgentSessionComposerSubmitRuntime.claim` the order
   becomes:
   1. build and store the capability;
   2. set `activeComposerSubmitAttempt` (:115);
   3. publish `composerClaimChanged` (:121).

   `release` (:143-151) and claim failure remove the capability before unpublishing.
2. **Stop classification.** `AgentSessionLinkStopAdmission.classify` maps
   `isComposerSubmissionInFlight` **with a stored capability** to `.pendingStart` instead of
   `.blocked(.targetBusy)` (StopTransaction :46). `withdrawPendingStartForSessionLink` and the local
   Stop target consume it: invalidate the stop fence, release the claim, restore the draft, and
   manufacture no attempt.
3. **Upgrade without a gap.** When the runner prologue synchronously begins the attempt and sets
   `.running` (AgentModeRunService.swift:458-462), the start owner swaps the pending-start
   capability for active-run admission in the same MainActor turn. There is never a visible
   starting/running state without one of the two.
4. **Other starts.** Typed ACP follow-ups and continuation producers (session-keyed, §2.5),
   initial-worktree preparation that belongs to a composer claim, and self-compaction admission
   (M9.2c) register before their visibility flags. Execution-location changes that are not starts
   stay `targetBusy`.
5. **Host adoption.** Capabilities live in the scope, never in the VM. A window closing during a
   pending start leaves the start cancellable from MCP, the monitor or a placeholder.

### 2.9 Presentation-less projections

`AgentSessionPresentationRuntime` gains one host-installed **detached sink** per scope. It is used
when no lease sink is attached to a session. It handles only app-level effects: actionable macOS
notifications (turn complete, failed, needs attention), monitor readiness, and sidebar badge
attention, through existing app owners. It never touches VM `@Published` state. Lease sinks keep
the existing generation-token semantics; a stale detach cannot disconnect a newer presenter.

### 2.10 Isolation

- **UI state** (VM `@Published` properties, transcript presentation records, composer, sidebar
  state) stays VM-owned and `@MainActor`. Hosts never write it; they publish through sinks.
- **Runtime** (`Scope`, host, host registry, presentation runtime and the handoff entry) is
  `@MainActor`. The justification is explicit: these types mutate `AgentTabSession`, which is
  `@MainActor` observable state shared with presentation, and I4's atomic release-and-claim relies
  on MainActor serialization instead of a lock. Provider IO stays off-main in existing controllers
  and actors (`DomainAgentRunSessionStore`, Codex/Claude transports).
- **No blanket changes:** no new `@unchecked Sendable`, no `nonisolated(unsafe)` and no new
  actors. Async joins are MainActor `Task`s. Deadlines reuse the checked-continuation gate pattern
  (`PreparedOversightShutdownGate`). Weak VM captures are allowed only in sink closures, never in
  runtime hooks; a nil VM must mean "no presenter", not "skip runtime work" (R1).

### 2.11 Composition with the M9.3 window-free host

M9.3b's host is built around `AgentSavedSessionTargetLoader.loadRuntime` and a caller-retained
scope, with real `AgentModeRunService`, MCP route, link endpoint host, provider coordinator and
`AgentSessionStorageInputs`. M9.4 needs four things from it:

- **(a)** The same host type is the **only** execution composition. The visible VM leases a host;
  it does not construct runtimes. **Decision D7: M9.3b owns this visible-VM cutover.** M9.4
  phase 1 starts only once M9.3b has delivered host-composed visible sessions.
- **(b)** The host registry that replaces `preparedOversightWindows`, `retiringPreparedOversightWindows`
  and `AgentSessionCarrierResolver.preparedSessionRuntimes` is keyed by host, can hold
  multi-session window hosts, and exposes lease, retention and per-session retirement.
- **(c)** Route identity is host-allocated, in the same ID space link endpoints use today (D8:
  shared allocator; typed route IDs are deferred to M10). Window IDs stop being runtime route IDs.
- **(d)** The host owns its API-settings lease and canonical workspace/context inputs, so window
  teardown (`apiSettingsViewModel.prepareForWindowClose`, root unloading) cannot remove a running
  session's resources.

With those in place, a saved-target host is a host born with no lease, and a window host is a host
born with a lease. Detach, handoff and drain are identical for both.

### 2.12 Links and oversight

- Live-consent links keep their endpoints across detach, because endpoints are host-route keyed.
  Send, wake, watch and Stop continue to reach the detached session. The disjoint link, notices,
  claim and wake owners are untouched.
- Parking for same-process reopen (oversight doc :454-500) is triggered by **endpoint retirement**,
  not window close.
- A visit handoff parks and re-establishes the link at the newly visited binding through the
  existing mechanism (`releasePreparedOversightOwnerForVisit` :355-357 comment).
- Doc updates belong to the implementation PR:
  - "Authority and UI ownership have separate lifetimes" (:51-64) generalises to all hosts.
  - "Window close still revokes live authority…" (:456) is replaced by "host retirement revokes…".

## 5. Risks and decisions

### Risks

- **R1 – Hidden VM dependencies.** Runtime hooks that capture `[weak self]` VM references
  degrade silently to no-ops once the VM deallocates; `linkExecutionRuntime.Commands.isAvailable`
  (VM :3306) is one example. *Mitigation:* test 5.1, plus a pre-cutover search of runtime-hook
  captures. Phase 1 is blocked on M9.2c and M9.2d retiring the remaining callbacks.
- **R2 – Interaction deadlock.** A detached run waiting for approval, combined with a deferred
  visit, could wait forever. *Mitigation:* placeholder interaction commands (§2.6) and test 2.4;
  notifications from the detached sink.
- **R3 – Resource lifetime.** Tool calls from a detached run after the window unloads its roots or
  stops its MCP server. *Mitigation:* precondition P1; never rebind a live route.
- **R4 – Invisible background work.** Users may not notice runs that outlive their window (cost,
  CPU, provider quotas). *Mitigation:* monitor/sidebar "running in background" rows with Stop,
  notifications and close-confirmation copy.
- **R5 – Last window and quit.** Closing the last window quits today unless MCP background mode is
  active (AppDelegate.swift:226-229). Quit cancels within 2 s. *Resolved by D4*, with residual
  risks: (i) a windowless app may surprise users, mitigated by notifications and the close-copy;
  (ii) auto-terminate must not race a window that is opening, so the registry re-checks window
  count and background mode in the same MainActor turn as the terminate request (tests 1.13–1.14);
  (iii) an `unsettled` host keeps the app alive until the user quits explicitly.
- **R6 – Fixture churn.** About 50 test sites use `prepareForWindowClose()` as cancel-and-teardown.
  Flipping close semantics without an explicit fixture teardown leaks providers or scopes across
  tests and causes order-dependent failures (compare the Oracle registry ordering issue in the
  M9.1 gate notes).
- **R7 – VM-owned coordinators.** `codexCoordinator` and `claudeCoordinator` are stopped by the
  VM today (VM :5057-5058). They must be host-owned (M9.3b provider/coordinator host) before
  detach, or stopping them on close cuts off detached runs.
- **R8 – Per-session release in shared scopes.** Scope-wide state (interaction runtime `routeID`,
  link execution, provider input) stays installed for the remaining sessions. Release must not
  tear down scope-wide services while a sibling is retained.
- **R9 – Never-settling hosts.** A wedged provider keeps its host alive indefinitely.
  *Mitigation:* existing Stop deadlines, visible `unsettled` state, the quit budget. A forced
  release is never allowed.
- **R10 – Parking semantics shift.** Moving launch-coordinator parking from window close to
  endpoint retirement changes when `noteWindowClose` runs. The existing restoration and
  duplicate-window tests must be re-baselined deliberately, not loosened.

### Decisions

Recorded 2026-11-10. The user decided Q1, Q4, Q6 and Q7 directly. For Q2, Q3, Q5 and Q8 the
recommendation stood without override, so it is adopted as the decision. The original options are
kept for the record.

- **D1 (was Q1) – Which runs survive close?**
  - *Options:* (A) all writer-owned runs detach; (B) only managed runs (link-managed,
    MCP-controlled, delegation children) detach, and ordinary user runs are still cancelled on close.
  - *Decision: A.* All writer-owned runs detach on close. "Stop Sessions and Close" stays the
    explicit stop choice, and "close cannot terminate" is a single rule with no run-kind exceptions.
  - *Applied in:* §2.3 close confirmation; tests 1.1 and 1.9.
- **D2 (was Q2) – Placeholder interactivity.**
  - *Options:* a read-only projection with Stop and pending interactions, or composer steering of
    the detached session through the writer.
  - *Decision:* read-only projection with Stop and pending interactions. No steering in M9.4;
    composer input stays a local draft until the handoff.
  - *Applied in:* §2.6.
- **D3 (was Q3) – Stash/archive.**
  - *Options:* keep them as explicit cancelling lifecycle commands (current documented policy and
    authorization), or reclassify them as presentation changes.
  - *Decision:* keep them explicit and cancelling, authorised as `control`. Out of M9.4 scope.
  - *Applied in:* §1.2.
- **D4 (was Q4) – Last-window close with live hosts.**
  - *Options:* (A) automatic background mode; (B) confirm with "Keep Running in Background" /
    "Stop and Quit".
  - *Decision: A.* When the last window closes with live hosts, the app keeps running without
    windows until the runs settle (then terminates through the normal path) or the user quits
    explicitly. Explicit quit keeps the bounded 2 s drain and reports unsettled work. This changes
    `applicationShouldTerminateAfterLastWindowClosed` (AppDelegate.swift:226-229).
  - *Applied in:* §2.3 last-window flow; §2.7; §3.1; tests 1.13–1.15; R5.
- **D5 (was Q5) – Non-quit drain deadline.**
  - *Options:* stay unbounded in time (retain until settled, as prepared owners do today), or add
    a soft deadline that only escalates the warning.
  - *Decision:* a soft deadline escalates the `unsettled` warning and **never** releases the
    writer.
  - *Applied in:* §2.5.
- **D6 (was Q6) – Workspace switch mechanism.**
  - *Options:* (A) one host per (window × workspace epoch); (B) a presented-subset filter over one
    window scope, which breaks the M9.1 rule that VM accessors forward to the scope map.
  - *Decision: A.* A workspace switch detaches the old workspace's sessions to their host, where
    live ones keep running, and attaches the window to the new workspace's host. Switching back
    re-leases the window's previous host for that workspace while it is still alive.
  - *Applied in:* §2.3; phase 3; test 1.7.
- **D7 (was Q7) – Who cuts the visible VM over to host composition?**
  - *Options:* M9.3b, or the first phase-1 task of M9.4 (size L).
  - *Decision:* **M9.3b owns the visible-VM cutover** (§2.11 a).
  - *Rationale:* D1, D4 and D6 make sessions routinely outlive windows, so every session must be
    host-composed from creation. A future headless/daemon mode makes host composition the product,
    with windows as optional clients. One composition path, the one a daemon would use, avoids
    building a saved-target-only path and reworking it later.
  - *Consequence:* M9.4 phase 1 starts only after M9.3b delivers host-composed visible sessions.
  - *Applied in:* P1; §2.11; §3.2; §3.3.
- **D8 (was Q8) – Route identity space.**
  - *Options:* host route IDs share the window-ID allocator, so link endpoint and MCP route types
    are unchanged; or endpoints switch to a typed route ID.
  - *Decision:* share the allocator in M9.4 and leave typing to M10.
  - *Applied in:* §2.11 c.
