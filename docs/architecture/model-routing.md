# Model Routing and Decision Services

Current as of 2026-10-13. Routing uses bundled profile annotations only; remote routing-profile update machinery has been retired.

## Authorities and dispatch

Model Router and Auto Effort are independent consumers of one text finite-choice decision layer. Each consumer owns its policy, bounded privacy envelope, opaque-choice map, freshness checks, and local fallback. `DecisionServiceRegistry` contains compile-time `DecisionServiceRegistration`s; primitive text/finite-choice capabilities and concrete request bounds determine compatibility. The registry performs exact ID lookup and never substitutes another service. `DecisionCoordinator` reserves a request before suspension, validates the request and returned opaque key/evidence, captures readiness generation and acceptance-policy version, and settles once. Caller cancellation synchronously claims `.cancelled`, including when a service ignores cancellation; late results cannot acquire an old reservation.

Jev and OpenAI Decisions are transport/acceptance adapters. They own their own credentials, readiness, evaluator, wire translation, timeout, response interpretation, and acceptance versions—not RepoPrompt CE's Router or Auto Effort instructions. The generic request contains exactly one named text finite-choice question in v1. A selected key is advisory until the consumer resolves it through its invocation-local map and the execution host revalidates the target. No decision service authorizes an executable model or effort.

The execution provider's catalog and availability/auth context are authoritative for exact executable models, supported parameters, and efforts. `RoutingExecutionMetadataAdapter` captures an immutable snapshot scoped to selection surface, allowed/connected providers, availability, and catalog revision/digest. Model Router admits only the maintainer-curated Codex/Claude families listed below when their exact executable targets appear in that snapshot. Unknown model IDs remain preserved in provider catalogs for manual selection but are not automatic Router candidates. Unknown raw efforts remain metadata unless that provider's execution bridge can actually submit them. Routing profiles may add dated quality/cost guidance and neutral effort descriptions but cannot add executable targets or override provider facts. `RoutingModelProfileResolver` resolves exact, provider-scoped alias/family, or explicit unknown evidence; ambiguity resolves unknown rather than authorizing a Router candidate.

## Model Router

The app-global Router toggle and exact selected service are durable. Enabling Router affects new user-created Agent Mode sessions and RepoPrompt CE-managed subagent starts before provider submission; it does not reroute established sessions, continuations, steering, or explicitly pinned compound model/parameter selections. Per-scope provider selections are preferences: an available selected provider narrows that scope's candidates to it; when it is unavailable, routing considers the other available shortlisted provider. The candidate builder takes one provider-authoritative snapshot and one immutable profile snapshot for the model→effort transaction. It selects at most one advertised executable base model from each of the eight curated families, strongest-first within each provider so judge position bias and capacity truncation favor capability: Codex Sol, Astra, Terra, Luna; Claude Opus, Fable, Sonnet, Haiku (Settings still lists families lightest-first). Primary user-created sessions are restricted to the strong and frontier classes (Sol, Astra, Opus, Fable) before capacity truncation; light and balanced families (Luna, Haiku, Terra, Sonnet) remain available only to subagent routing. Luna and Sol use the existing approved-family helper to prefer the newest advertised version, falling back to their original aliases. Profiles annotate admitted candidates but never expand this list. If fewer than two shortlisted executable models are available, routing falls back locally without asking a decision service.

`ModelRouterDecisionPolicy` (`rpce.model-router`, version `2026-10-26-v2`) constructs one generic model-choice request and, after a valid model choice, one effort-choice request for that selected model through the **same captured service**. The policy owns the capability-first instructions and semantic byte budget: tier descriptions are capability evidence, missing benchmarks mean unknown rather than weak, and price only breaks ties between comparably capable models. A model-stage selection whose service-reported confidence is below 0.4 is treated as an abstention and falls back locally. It preserves the saved directive, all opaque keys and provider/model identities, an unknown-evidence marker, and both ends of a long task before optional profile, role, and rubric evidence. The executable-target map never crosses the service boundary. Before application/submission the host rechecks Router revision, ownership, provider support/snapshot scope, and target validity; rejected submission rolls back the complete temporary target without changing manual defaults.

A missing, incompatible, unavailable, failed, abstaining, or invalid exact service never triggers backend failover. Model-stage failure keeps the current selection or role default; effort-stage failure keeps the chosen model at provider-default effort. Explicit cancellation or stale ownership blocks submission instead of applying a late advisory result. Routing requires at least two eligible models; a smaller frontier falls back locally without a decision-service request.

### Router privacy envelope

For a routed new task, the selected service receives bounded user-authored task text (or a deterministic beginning/end excerpt for a long task), saved routing guidance, role references, and candidate provider/model/effort descriptions with advisory profile evidence. The local task-text ceiling is 4,000 characters / 16 KiB, independent of a service's larger capability bound. RepoPrompt CE does not append attached files, workspace context, repository/file paths, selections, diffs, transcript/history, workflow templates, tool results, system prompts, session IDs, provider credentials, or downstream provider state. Text the user wrote in the task or guidance **can itself contain** paths or secrets; masking is best effort, not anonymization. The full task still goes to the chosen execution provider under its normal submission path.

## Local usage balancing and Fast opt-in

Tip’s quota-aware usage balancing remains a local, opt-in policy. It can substitute a currently executable Codex/Claude peer before the effort decision; peers carry the same catalog scope and profile identity checks as Router choices. Explicit cancellation blocks submission even after substitution. The separate paid Fast opt-in only admits provider-advertised Fast targets to Router effort choices; it never synthesizes a model or enables Fast implicitly.

## Auto Effort

Outside a Router-owned fresh start, the composer retains the provider's manual effort picker alongside the informational Auto Effort status. Users can inspect and change the fallback effort without disabling Auto Effort, including for custom workflows and unavailable decision services. Normal provider, MCP-ownership and active-run control locks still apply.

Auto Effort is separately enabled and defaults off. Its exact decision-service selection persists as a raw ID; its revision is process-local and held in memory. An absent service field from older settings resolves to Jev **in memory** without writing it. Explicit blank/unknown IDs remain stored and unavailable; they do not become Jev. Router and Auto Effort may select the same service or different services, with independent demand and revision cancellation. A selection while disabled does not bootstrap a service; viewing Settings cards does not create demand.

For an eligible composer turn or MCP first start/settled follow-up, Auto Effort operates only on the already-selected exact model. A first start already routed by Model Router retains Router's effort decision. Active steering, slash controls, custom workflows, unsupported/alias/default model selections, and models without at least two executable provider-advertised efforts retain manual behavior. `AutoEffortDecisionPolicy` (`rpce.auto-effort`, version `2026-10-07-v1`) sends one effort-only finite-choice request. It maps opaque keys to provider-authorized raw efforts locally; future effort names receive neutral, unprofiled descriptions rather than guessed cost/quality. The send path rechecks Auto Effort revision and service, workflow generation, selected model, manual effort, provider support, and decision ownership before applying an ephemeral result. It does not rewrite saved model or effort preferences. Failure, refusal, stale state, incompatible capability, or unavailable service keeps the current/manual effort—never a second service.

The Auto Effort envelope contains only the selected model ID, provider-advertised effort choices, a short locally best-effort-masked excerpt of the **current** user turn, and the fixed category of a selected built-in workflow. It adds no workflow template, attached file, tool result, earlier conversation, workspace context, or provider credential. User-authored prose can still disclose sensitive content. The pill's pending/last-choice indicator is send-time feedback, not proof of provider completion or prompt-cache savings. Cache preservation is not guaranteed.

## Service acceptance and credential isolation

Jev retains the dedicated `JevRouterAPIKey` secure-storage account, TypeSafe model-list readiness check, pinned `jev-1.13.0` evaluator, one `route` question on `/v1/systemone`, five-second deadline, and no RepoPrompt CE-layer retry. Its interpreter requires exact question/choice coverage, a normalized probability distribution, and a unique argmax matching the declared choice. A generic decision still submits only one question; Jev's private batch DTO does not enlarge the shared contract.

OpenAI Decisions retains the separate `OpenAIDecisionsRouterAPIKey` account, documented `POST https://api.openai.com/v1/decisions` endpoint, pinned `gpt-6-luna` evaluator, fixed synthetic validation request, five-second full-body deadline, 64 KiB response cap, redirect refusal, and no retry/hedge. Validation may incur a small charge and proves access only at that moment. The interpreter requires one correctly named choice answer or typed refusal, exact unique option/probability coverage, bounded evidence, and modeled usage; it does **not** impose Jev's argmax or distribution-sum rule. Status-only 401/policy and quota failures preserve the stored key rather than assuming bad credentials. The [first-party contract record](../plans/openai-decisions-contract-2026-10-07.md) is the adapter boundary.

Neither adapter reads, copies, compares, or falls back to the other's key, a general OpenAI/Codex key, or an execution-provider credential. Generic Settings sees only redacted registration presentation/actions and credential-context summaries, never a stored secret. Startup validation is noninteractive and at most once per credential generation; explicit credential actions have their own ownership/fencing. Removing the selected Router service's secret disables Router only under the captured/current selection and revision fences. Auto Effort intent and selection remain unchanged, but its result falls back to manual effort until the service is ready. A dedicated OpenAI project/key is recommended for usage attribution and project-level controls; a separate key alone is not a hard spend boundary, and deliberate manual reuse shares accounting.

## Persistence, Settings, and bundled profiles

Router fields remain under `scalarPreferences.modelRouter` (v9 base, v10 scoped provider/guidance fields). Legacy role/allowed-provider raw arrays are retained for schema/rollback compatibility but no longer construct candidates. Auto Effort's optional independent `scalarPreferences.agentMode.autoEffortBackendRawValue` requires schema v12 when present; an older writer rejects it rather than silently interpreting a non-Jev selection as Jev. The deprecated `scalarPreferences.modelRoutingProfiles.remoteUpdatesDisabled` and `lastCheckAt` values remain Codable schema-v12 compatibility data; they are inert and are preserved through unrelated settings edits. The content-derived schema fence still requires v12 when either value is present. Unknown raw IDs and unknown sibling settings survive unrelated edits; secrets are never in this document. See [settings persistence](settings-persistence.md).

The Agent Decisions Settings tab retains **Model Router**, **Auto Effort**, and registration-driven **Decision Services** sections, plus Tip’s usage-balancing and paid Fast opt-in controls. Provider-owned model discovery remains independent of routing profiles. The Update models action requests eligible provider-owned refreshes; there is no routing-profile feed. Each consumer has its own compatible-service selector and Configure action. Unknown selections remain visibly unavailable. Configure only expands/focuses the exact service card; it never selects/enables a consumer, validates a key, advances a credential generation, or creates demand. Readiness is a passive, keyed projection from the app-global runtime. Window-local disclosure/secret drafts and action tokens protect against stale credential feedback. Cards display backend-owned privacy/pricing/technical notices and dedicated-project wording.

Bundled routing profiles are the only profile source. The JSON bytes compiled into `BundledRoutingProfiles.swift` are decoded with strict duplicate-key/schema validation by `RoutingProfileDocumentDecoder`; `RoutingModelProfileResolver` adds advisory annotations only and cannot create executable models or efforts. `RoutingModelProfileSnapshot` owns the content-derived digest and identity used by candidate freshness checks. `RoutingProfileStore` is an immutable bundled-snapshot accessor. There is no remote coordinator, fetch transport, cache, verifier/trust store, profile activation, or remote lifecycle hook. Profile identity changes fence already-captured candidate work; provider catalogs remain the sole authority for executable targets. See [bundled profile publication boundary](routing-profile-publication.md).

## Validation boundary

Deterministic suites cover exact registration/capability filtering, a fake third service, all four Router/Auto Effort service-demand combinations, both adapters' wire and privacy contracts, no-failover/manual fallback, cancellation/settlement, provider-authoritative metadata, bundled profile precedence/freshness/strict decoding, and Settings migration/credential isolation. Real Settings pointer/VoiceOver behavior, composer and MCP smoke, and any paid service-quality check remain separate live verification; they are not established by these unit tests or by this document.
