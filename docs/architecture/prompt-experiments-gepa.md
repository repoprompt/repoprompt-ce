# Prompt Experiments and upstream GEPA

Prompt Experiments is a DEBUG-only lab for improving RepoPrompt CE's built-in prompts. Upstream GEPA searches candidate prompt bodies; the app owns prompt rendering, connected-model calls, grading, budget admission, persistence, approval, and source-patch review. Results are evidence, not automatic promotion.

## Registry and suites

`BuiltInPromptRegistry` loads UTF-8 prompt bodies from `AppResources/Prompts/<id>/prompt.md` (packaged under `Contents/Resources/Prompts`). It records a SHA-256 of the file bytes and removes one trailing LF for rendering. Production and `ConnectedModelHarness` share the renderer; an experiment override applies only to its selected prompt ID and evaluation. User-edited stored prompts and custom planning prompts retain their precedence. The lab optimizes the built-in baseline, never a user's edit.

Each eligible prompt has a checked-in `suite.json` and, for model judging, `rubric.md` beside it. Schema 1 declares stable case IDs, training/validation/hidden-test splits, prompt variant, grader and score range. A case's `input` is the user's instructions; optional `file_tree` and `files` carry frozen context. `ConnectedModelHarness` (and the judge) package each case with the production `PromptPackagingService.buildAIMessage` / `AIMessage` builders, so the target sees the same `<file_tree>`, `<file_contents>` and `<user_instructions>` structure as a real Oracle request. The loader rejects malformed or mismatched suites before model spend. Oracle Plan's `oracle-plan-v1` suite contains twelve compact frozen-context planning tasks (six training, three validation, three held out).

A model-judge rubric is a weighted binary checklist (CheckEval-style): lines of the form ``- `id` (weight W): question`` are answered by the judge, and ``- `id` (weight W, host: kind params): description`` lines are computed deterministically by the host (`required_sections sections=A|B`, `no_code_patch max_block_lines=N`, `paths_in_context`). The loader rejects holistic or malformed checklists. The judge returns, for every judge check exactly once, a boolean `pass` plus, for a failure, a verbatim failing `span` (empty for an omission) and a concrete `fix`; one format repair is allowed. The score is the weighted pass fraction mapped into the suite range, and the proposer-facing feedback lists failing checks (span and fix) before the passing ids. Oracle Plan's checklist covers grounded current state, seam reuse, resolved decisions, invariants, file-by-file impact, ordering, focused tests, explicit assumptions, no fabrication and proportion, plus host checks for the prompt's required sections, no code patches, and paths grounded in the case context. The default judge is a different model from the reflection model, and choosing the same model is a validation error. Held-out feedback is redacted at the proposer boundary while host-side reviewer evidence remains stored.

## Approval, execution and recovery

The `prompt_experiment` MCP tool exposes `targets`, `create_or_update`, `request_approval`, `run`, `status_or_wait`, `cancel` and `propose_patch`. It cannot approve spend or apply a patch. One native approval binds prompt/resource and suite/rubric hashes, resolved execution/reflection/judge targets, GEPA settings, runtime pin, a cumulative search cap and a separate baseline-calibration line. Changing an approved authority creates a new experiment requiring approval. Approval starts the first run; later explicit `run` calls resume within the remaining cap.

## Budget shape

The search cap pays for GEPA's seed validation pass, proposals, and a held-out reserve of |hidden| that scores only the incumbent. Defaults are minibatch 2, merge off, `current_best` parent selection and perfect-score skipping, so a rejected proposal costs 2m and an accepted one 2m+|V|. GEPA's own metric-call stopper is not used (it restarts per process and counts ledger replays); the worker's `LedgerBudgetStopper` reads the ledger's remaining search admissions from every evaluation reply and never starts an iteration that could not finish (remaining < 2m+|V|). Because replays are free, the worker also skips proposals identical to the parent or to an earlier proposal and caps reflection calls at the search cap. For oracle-plan-v1 (6/3/3) a cap of 25 leaves 19 after the reserve and seed pass: about four proposals (three if one is accepted). `targets` reports this as `budget_guide`.

Baseline calibration is a separately approved line (|hidden| today) spent before search: the seed's held-out scores. They depend only on the prompt ID, seed SHA, suite and rubric SHAs, and the execution and judge models, so they are cached across experiments under `calibration/<key>.json` in the store root; a cache hit spends nothing. A calibration provider/judge failure leaves the held-out baseline unavailable without failing the search.

## Reflection

The worker owns the reflection prompt through GEPA's `custom_candidate_proposer`. Per minibatch case the reflection model sees the case request (instructions only, not frozen file contents), the score, the grader feedback, and a head+tail output excerpt (3 KB + 3 KB with an omission marker). GEPA's `_budget` and other `_`-prefixed bookkeeping never reach it. Every embedded text is fenced with a backtick run longer than any inside it, and the reply must use the BEGIN/END candidate envelope. Each evaluation records candidate and output characters plus target token usage when reported; candidates carry per-text averages computed from the whole ledger.

`GEPARunController` runs the pinned upstream GEPA worker over a credential-free NDJSON bridge. `ConnectedModelHarness` makes prompt-only provider calls with no tools. `BudgetLedger` durably admits each logical evaluation before spend, does not refund admissions, and prevents duplicate IDs from re-spending. Swift owns classified transient retries and records each provider invocation. Budget exhaustion is a soft stop with the saved incumbent (`stopped_budget`), not an invented winner or a fatal evaluation. In-stream provider errors are classified (rate limit, overload/503, transport) so transient failures retry. A malformed judge reply gets one format repair per evaluation; judge JSON may be surrounded by prose. A reflection reply without the candidate envelope, or with an empty candidate, is a skipped proposal, never accepted as prose. Held-out scoring is report-only: its reserve has its own exhaustion flag, and a held-out provider/judge failure reports that score as unavailable without discarding the completed search. Baseline (from calibration, with its source) and best held-out averages appear in the run assessment and review sheet. Runs and content-addressed evidence survive restart. An interrupted run is marked inconclusive, never silently replayed; explicit resume reconciles the checkpoint and ledger and rejects ambiguous in-flight callbacks.

The app packages CPython 3.11 and pinned GEPA 0.1.4 in DEBUG builds. Python receives no provider credentials, workspace authority or source-write access. Release builds do not ship this lab. The canonical debug store is schema 8 and the ledger schema 2; earlier lab records are discarded rather than migrated. Human-readable views are projections, not authority.

## Reviewed source patch

A completed or stopped-budget run can retain candidate indices. `propose_patch` or the Studio creates a proposal for one index after verifying the explicitly configured source checkout's `AppResources/Prompts/<id>/prompt.md` is a contained regular file without symlink components and still matches the experiment's baseline SHA. Candidate text and a one-file unified diff are stored as artifacts. The packaged app bundle is never edited.

The native card/Studio review sheet shows the full diff and run evidence. Only its **Apply to Source** or **Reject** actions decide a proposal. Apply archives the exact previous prompt under `previous/<sha>.md`, rechecks the source SHA immediately before atomic replacement, and fails with a clean conflict if it changed; it does not merge. Reject preserves the proposal and run evidence. `PromptViewModel` includes validated archived defaults in canonical-upgrade recognition so unedited stored Architect/Review and planning copies upgrade after a reviewed prompt change, while user edits remain untouched. The source checkout defaults to the one the DEBUG build was compiled from (derived from `#filePath`, like `BuiltInPromptRegistry.defaultPromptsDirectory`, because conductor's `open -n` launch does not forward shell environment); `REPOPROMPT_PROMPT_EXPERIMENT_SOURCE_ROOT` overrides it. No bundled-resource fallback is a write target.

## Add a prompt to the lab

1. Give the plain-text built-in a `BuiltInPromptID`, `prompt.md` resource and production rendering call site, preserving user-override precedence.
2. Add a small `suite.json` with stable training, validation and hidden-test cases plus `rubric.md` for model judging. Keep expected outputs and grading notes host-side.
3. Add resource, rendering, suite-loading and old-default-upgrade tests; verify app packaging and both products.
4. Run a bounded debug experiment, inspect retained evidence, and review the one-file source diff before applying. Commit source changes only through the ordinary contribution workflow.

A future `ContextBuilderHarness` may evaluate repository-aware workflows using a per-evaluation snapshot and headless `repoprompt-mcp`; it is not implemented. Never substitute the active window's workspace authority for that isolation boundary.
