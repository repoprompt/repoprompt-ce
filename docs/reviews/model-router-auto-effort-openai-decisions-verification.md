## Supported behavior and boundaries

### Model Router

- The app-global Router toggle and exact service ID persist. When enabled, Router makes advisory choices for new user-created Agent Mode sessions and RepoPrompt CE-managed subagent starts before provider submission. It does not reroute established sessions, continuations, steering, or explicitly pinned compound model/parameter choices.
- Candidates and executable parameters come from an immutable snapshot of the execution provider's catalog and availability/auth context. Router admits only the original eight curated Codex/Claude families when advertised as executable, and requires at least two eligible exact models. Profile metadata may inform descriptions but cannot expand the shortlist or add executable efforts.
- The selected service receives one finite-choice model request followed, only after a valid choice, by an effort request for that model through the same captured service. Opaque candidate IDs stay local; the host revalidates provider support, ownership/revisions, and target before submission.
- Missing, unavailable, incompatible, failed, refusing, stale, or invalid routing does not fail over to another decision backend. Model-choice failure keeps the current selection/role default; effort-choice failure keeps the chosen model at provider-default effort. Stale/cancelled ownership blocks application/submission.

### Independent Auto Effort

- Auto Effort is a separate, default-off consumer with its own exact service selection, enablement, demand, and revision. Router and Auto Effort may select different services. Selecting a service while disabled or merely viewing its Settings card creates no demand.
- It applies only to eligible composer turns or MCP first-start/settled follow-up, for the already-selected exact model and provider-advertised efforts. Router's effort choice remains authoritative for a first start already routed by Model Router. Active steering, slash controls, custom workflows, unsupported/alias/default model selections, and models with fewer than two executable advertised efforts keep manual behavior.
- One effort-only decision maps opaque keys to provider-authorized raw effort values locally. The result is ephemeral; saved model/effort preferences are not rewritten. Failure, refusal, stale state, or unavailable service keeps current/manual effort, with no second service attempted.

### Services, credentials, and validation

- Jev and OpenAI Decisions are isolated adapters with distinct readiness, validation, transport, acceptance, and secure-storage accounts (`JevRouterAPIKey` and `OpenAIDecisionsRouterAPIKey`). Neither reads, copies, compares, nor falls back to the other's key, a general OpenAI/Codex key, or an execution-provider credential.
- Jev uses its TypeSafe model-list readiness check and pinned `jev-1.13.0` evaluator. OpenAI Decisions uses the documented fixed `POST https://api.openai.com/v1/decisions` route and pinned `gpt-6-luna` evaluator. OpenAI credential validation is a fixed synthetic request, may incur a small charge, and only proves access at the time of validation. Its five-second full-body deadline, 64 KiB response cap, redirect refusal, and no-retry policy are RPCE adapter limits, not provider guarantees.
- Generic Settings receives redacted service presentation/readiness, not stored secrets. Configure expands/focuses the exact service card; it does not select or enable a consumer, validate a key, or create demand. Status-only OpenAI 401/policy and quota failures do not prove a key invalid and preserve it. Removing a selected Router key disables Router only under selection/revision fences; Auto Effort intent/selection remain, with manual fallback until ready.

### Privacy and fallback

- Router sends bounded user-authored task text (up to 4,000 characters / 16 KiB locally, excerpting long text), saved routing guidance, role references, and bounded candidate descriptions/advisory profile evidence. It does not append attached files, workspace/repository paths or context, selections, diffs, transcript/history, workflow templates, tool results, system prompts, session IDs, credentials, or downstream provider state. The complete task still goes to the chosen execution provider by its normal path.
- Auto Effort sends only the selected model ID, provider-advertised effort choices, a short locally best-effort-masked excerpt of the current user turn, and the category of a selected built-in workflow. It excludes workflow templates, files, tools, earlier conversation, workspace context, and credentials.
- User-authored task/guidance/turn text can itself disclose sensitive material. Masking is best effort, not anonymization. A decision is advisory, never execution authorization. There is no automatic backend or local-to-remote credential fallback; failures retain the current/default/manual choice as described above.

### Bundled routing profiles and persistence

- Routing profiles are bundled, strictly decoded advisory annotations only. The runtime has no remote profile updater, cache, verifier/trust path, transport, activation stream, or profile-fetch lifecycle. Unknown provider-authorized models can remain manually selectable, but are not Router candidates unless they match the curated shortlist; profiles cannot add executable models or efforts.
- The removed schema-v12 `scalarPreferences.modelRoutingProfiles.remoteUpdatesDisabled` and `lastCheckAt` values are deprecated and inert. Codable support and the content-derived v12 schema fence remain so unrelated settings edits round-trip these fields; active settings code does not read or write them.

## Practical reviewer checklist

For source/tests, verify the following contracts and failure cases:

- [ ] Toggle Router and Auto Effort independently; confirm independent exact selections and service demand, including different service selections and no bootstrap from disabled selection/card viewing.
- [ ] Verify Router scope (new task/subagent start only), exact provider-authorized candidate admission, at least two candidates, model-then-effort sequencing through one service, and stale/cancelled result rejection.
- [ ] Exercise unavailable/unknown service, failed/refused/invalid answer, stale state, and one-candidate frontier; confirm no service failover and preservation of current/default/manual choices.
- [ ] Exercise Auto Effort eligible and excluded cases, provider-advertised effort bounds, ephemeral application, and manual fallback.
- [ ] Confirm Jev/OpenAI key isolation, validation/readiness ownership, redacted Settings state, status-only 401/quota preservation, and fenced secret removal.
- [ ] Confirm bundled profile decoding/resolution is metadata-only; no remote profile or update-feed path exists.
- [ ] Review the Router Settings disclosure animation and focus changes: page/service/nested expansion, Configure expansion then scroll/focus, Reduce Motion, keyboard/VoiceOver labels and focus, and OpenAI credential-field mount/focus across collapse/reopen. Automated state/presentation assertions do not establish visible smoothness.

**Open integration review gap (pre-existing at HEAD, not an item-2 blocker):** MCP `agent_run.start` and `agent_explore.start` retain a routed target across later awaited setup before dispatch. The route checks its catalog snapshot before returning, but this later interval has not been deterministically tested for catalog/settings changes. No new continuous-invalidation contract is established here; this is not included in the bounded fixes or claimed verified.

For live/manual checks, do not use real credentials or incur provider charges unless separately authorized. Beyond the user's general visual pass noted below, representative installed/authenticated provider discovery, detailed Router Settings/VoiceOver behavior, target-count presentation, pointer/keyboard interactions, and transition smoothness remain **unverified** by the checks listed below. Composer/MCP live exercise and paid service quality are also unverified. Do not perform a production profile-fetch check: no such path remains.
